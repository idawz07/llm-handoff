local inference · gpu supervision

One GPU. Many engines.
Never a fight for VRAM.

Handoff Router is an OpenAI-compatible facade that supervises llama.cpp, vLLM, SGLang, Strata, NInfer — any local model server — as backends of a single endpoint. You name a model in the request; it drains whatever is running, stops its process group, waits until the card is actually free, and starts the engine that owns that model.

The problem it exists for

Local LLM tooling has gotten very good at many models, one engine. The hard case is narrower and meaner: many engines, one GPU, where each engine wants most of the card and a cold load costs minutes.

01 · overlap

Two loads, one card

A 50 GiB reload starting while a 27B unload is still releasing CUDA memory is how you get an OOM kill, a 40-minute page-cache rebuild, and a frozen desktop.

02 · ownership

Who owns the process?

Engines started by hand, by a job runner, or by a previous router process keep holding the port and the memory. Starting a second copy fights them for both.

03 · collateral

Work in the middle

A switch that kills a live 6,000-token stream, or evicts the embedder every time you change LLMs, makes a multi-engine box unusable in real workflows.

We are not here to replace the ecosystem. llama-swap, Ollama, LocalAI and GPUStack solve the general problem better and broader than this project does — they get Anthropic and image and audio endpoints, richer routing rules, hot config UIs, and cluster scheduling. This is the one constraint they leave uncovered, and everything here is MIT so you can take just that part.

How it works

One address, one API key, one switch lock. The engines stay on loopback; only the facade is reachable.

The handoff, step by step

  1. Resolve. The requested model id names a backend — a llama.cpp preset ID, or a declared selector.
  2. Reuse if possible. Right engine already healthy? No restart, no wait. Concurrent requests coalesce into one in-progress start.
  3. Drain. Stop admitting new work; let in-flight generations finish (drain_timeout_seconds). A slow client fails the switch — it never cuts the stream.
  4. Tear down the process group. SIGTERM, then SIGKILL, to the whole group, so orphaned CUDA workers go too. resident sidecars are left running on purpose.
  5. Wait for the card. Process-group exit plus a min_free_vram_mib gate from nvidia-smi. If an external supervisor already started the target and it is healthy, adopt it instead of starting a duplicate.
  6. Prove it servable. /health 200 and the model actually loaded (adapter-specific) before the first forwarded byte. You never get “model is not loaded”.
invariants

What never happens

  • Two non-resident backends owning the GPU at once.
  • A switch killing a live generation to make room.
  • A disconnected client leaving a half-started 50 GiB process.
  • A duplicate engine fighting a leftover one for the same port.
  • A config edit costing you a cold load.
  • A public model id leaking the upstream engine's name in a stream.

Features

swap

Engine-level switching

Any HTTP server with a health endpoint becomes a backend. Adapters for llamacpp, vllm, sglang, strata, ninfer; the unit of management is the engine, not the model.

safety

VRAM-gated handoff

Free-VRAM threshold, process-group teardown, one switch lock, and a lease reserved before the lock is released — the four things that stop overlapping loads.

adoption

Adopt, don't duplicate

Healthy leftovers — from a crash, a reboot, a job runner, or your own tmux — are matched by command-line fingerprint and taken over.

llama.cpp first

Your presets stay yours

Every --models-preset section becomes an addressable model ID automatically. /props, /slots, /models/sse and the llama.cpp web UI keep working — even pointed at non-llama.cpp engines, because props are synthesized.

zero diff

Adopt in place

A launcher shim over your existing llama-server path means your systemd unit, port, and API key never change. Only the router invocation enters the facade; everything else delegates byte-for-byte.

no cold reload

Config hot reload

Edit router-backends.yaml while serving. The active model is never restarted; changed launch lines apply on the next switch; a broken file is rejected and the running config stays.

reclaim

Idle TTL, cheap first

idle_ttl_seconds per backend, eviction ordered by evict_cost, negative values pin a model in VRAM. Off by default: keep a three-minute load warm until something else needs the card.

coexist

Resident sidecars

Embedders, rerankers, and small models marked resident: true survive every big-model switch instead of being evicted each time.

windows

Freeze the GPU

POST /router/freeze blocks model loads while ComfyUI, Blender, training, or a benchmark runs. thaw hands it back. Unloading is never blocked, so a window can still clear the model it is standing on.

visibility

Activity + logs

An in-memory lifecycle ring with durations, streamed over SSE (/router/activity, /activity/stream) and per-backend log tails at /logs/<backend>.

recovery

Crash-proof state

pid/pgid/boot-id persisted atomically. On restart: adopt what is healthy, reap what is stale, ignore what belongs to another boot.

tested

28 tests, no GPU

Real subprocesses and real TCP/SSE against fake backends: the whole switch matrix, coalescing, draining, cancellation mid-start, adoption, recovered process groups, the VRAM gate, reload, idle reclaim, coexistence.

Operations, in the API

# what owns the GPU right now, with idle time and eviction cost
GET  /router/status

# every id, with load state and which backend owns it
GET  /v1/models

# warm now (switches engine) / free the card now
POST /models/load     { "model": "flash-next-256k" }
POST /models/unload   { "model": "flash-next-256k" }

# a ComfyUI window: no model may load until you're done
POST /router/freeze   →   POST /router/thaw

# add a checkpoint while traffic is flowing; no restart, no cold load
POST /router/reload

# audit trail with durations, live
GET  /router/activity?limit=40
GET  /activity/stream
GET  /logs/llamacpp?lines=200

Events you can alert on

  • switch → backend_ready with duration_seconds — your cold-start SLO, measured.
  • switch_failed — includes the last observed free VRAM and a log tail.
  • idle_unload / idle_unloaded — VRAM you got back.
  • coexist — a resident backend deliberately kept warm.
  • config_reload / config_reload_failed — who changed what, and whether it was rejected.
  • restart_pending in /router/status — a config edit that applies on the next switch.

One helper for all of it: scripts/routerctl.py status | models | load | unload | freeze | thaw | reload | activity | logs | watch

Quickstart

  1. pipx install git+https://github.com/your-org/handoff-router.git
  2. mkdir -p ~/.config/handoff-router then copy config/router-backends.example.yaml there and set each engine's command, upstream, and process_match.
  3. Check it without touching the GPU:
    handoff-router --config ~/.config/handoff-router/router-backends.yaml --print-config
  4. handoff-router --config ~/.config/handoff-router/router-backends.yaml --port 8081 --api-key "$KEY"
  5. Name a model; the engine follows:
    curl -s localhost:8081/v1/chat/completions -H "Authorization: Bearer $KEY" -d '{"model":"flash-next-256k","messages":[{"role":"user","content":"hi"}]}'

…or adopt it onto the llama-router you already run

# moves llama-server aside, leaves a narrow shim in its place:
# only the --models-preset + --port 8081 invocation enters the facade,
# every other llama-server call delegates byte-for-byte to llama-server.real
HANDOFF_ROUTER_PRESET=$HOME/Models/router-presets.ini \
  deploy/install-dispatcher.sh
systemctl restart llama-router          # your existing unit, port, and key
curl -H "Authorization: Bearer $KEY" localhost:8081/router/status

Questions worth asking

Is this a proxy with extra steps?

It is a supervisor that happens to proxy. The value is in what happens before a request is forwarded: drain, process-group teardown, a VRAM gate, adoption, and model-readiness proof. Streaming stays incremental — only enough buffering to find a newline.

Why not just add more models to llama.cpp's router?

Because the other engines are not GGUF servers. We keep llama.cpp's --models-preset router as one backend with its LRU intact, and put the engines that cannot live inside it beside it.

Will it unload the model I'm using?

Not unless you ask. Idle reclaim is off by default (idle_ttl_seconds: 0), protected by idle_grace_seconds, never runs while a request is in flight, and can pin a backend with a negative TTL.

Multi-GPU?

No. The scope is deliberately one card: the failure mode it prevents is two-big-loads-on-one-GPU. For placement across cards and nodes, GPUStack or a Kubernetes path is the right tool.

Is the API key enough?

On that host, yes — treat it as root-equivalent, because POST /router/reload re-reads a config that launches arbitrary commands. Bind the facade to a trusted network or put auth and TLS at a reverse proxy.

What is missing?

Anthropic /v1/messages, image/audio endpoints, a first-class metrics exporter, richer coexistence solving, non-Linux process handling, and a web UI of our own (the llama.cpp one works). Contributions welcome — see CONTRIBUTING.md.
